## 这一轮改了什么

- 同一 URL 合并时，主行是排序赢家，与来源顺序无关。主行缺失 `summary` 时，另一家的 `null` 或 `""` 不能把顶层写成 `null`。只有非空摘要能补上缺失、`null` 或 `""` 的主行。provenance 仍按各源原来的 missing、`null`、`""` 或非空摘要记录。非空摘要不写进 `snippet`，`snippet` 也不写进 `summary`。两源两种顺序和三源都由 `scripts/test-v031-beta4.mjs` 覆盖。规则写在 [字段契约](./v0.3.1-beta1-fields.md)。
- `outcome` 五态出现在文本和 MCP `structuredContent`，包括 `isError: true` 的搜索结果。schema 用 zod 实测解析，不只在成功分支补字段。HTTP 200 且零条仍是成功。没有结果对象的意外异常不伪造 outcome。
- 引用 URL 和各源 provenance 保留非空片段。去重键仍去掉片段，`#a` 与 `#b` 仍是一行。不编造标题或来源。
- title、snippet、summary 全空时不再算命中。`warnings` 保留引擎和原始 URL（含片段）。不补标题或摘要。引擎本身成功时 outcome 仍是 `empty_success`。
- 轻量首页中文免 Key 说明改成完整句「自动搜索：免 Key 引擎。」引擎名单另起一行，不再把「引擎。」留成被换行切开的残句。取消后仍回到上一项已完成的菜单条目；这是 beta.2 已锁定的焦点，本轮不改成停在被取消的那一项。没有新入口。
- 全屏界面每次重绘先把备用屏幕整屏清掉再画。缩小或改字号后，旧的更宽画面不再留在新行的右侧。焦点、当前条目和已经打开的确认框保持原样。父机真实 XFCE 上「运行中改尺寸有残留、重启就干净」不能单独断定是重绘还是终端时序：进程只能按当时的 `columns`/`rows` 重画；若这次 resize 事件里的行列还不是最终格子，而且没有下一次 resize，这里无从知道最终尺寸。那部分不改界面结构。

## 升级、回滚、备份、还原

唯一权威步骤是这一节。同包里的 [beta.1 说明](./v0.3.1-beta1-release.md) 和 [0.3.0 说明](./v0.3.0-release.md) 是历史行为，不再给出 registry 安装命令。已封存的 beta.1 tarball 不改。

不要执行 `npm install -g search-boost@0.3.0`、`npm install -g search-boost@beta` 或 `npm install -g search-boost@0.3.1-beta.4`。registry 上没有这些版本。`@latest` 是别的已发布通道，不是这次回滚。

下面的路径不要照抄测试日志。测试用的临时目录不是用户目录。每次以本机 `search-boost` 打印的 `File:` / `文件：` 为准。

### 1. 查出这次进程真正使用的配置

```bash
search-boost config keys --show
```

输出里的 `File:` 或 `文件：` 就是 keys 文件。它的上一级是 `config`，再上一级是这个进程的 SearchBoost 根目录。设置了 `SEARCH_BOOST_HOME` 时，根目录是那个值，而不是 `~/.search-boost`。没设置时，根目录是 `~/.search-boost`，keys 文件是 `~/.search-boost/config/keys.json`。这条命令只打印打码后的 Key，不打印原文。全屏界面的「配置位置」显示同一个根目录。

文件还不存在时，没有东西可备份。安装软件包不会创建这个文件。

### 2. 在改软件包之前备份

备份放在配置根目录外面，避免后来的安装或还原把唯一副本盖掉。把下面的 `File` 行换成上一步打印的那一行：

```bash
file_line=$(search-boost config keys --show | sed -n 's/^File: //p; s/^文件：//p' | head -n 1)
case "$file_line" in
  '~'/*) keys="${HOME}/${file_line#\~/}" ;;
  *) keys="$file_line" ;;
esac
test -f "$keys"
store=$(dirname -- "$keys")
root=$(dirname -- "$store")
stamp=$(date -u +%Y%m%dT%H%M%SZ)
mkdir -p -- "$HOME/search-boost-backups"
chmod 700 "$HOME/search-boost-backups"
dest="$HOME/search-boost-backups/store-$stamp"
mkdir -p -- "$dest"
cp -a -- "$root/." "$dest/"
find "$dest" -type d -exec chmod 700 {} +
find "$dest" -type f -exec chmod 600 {} +
cmp -- "$keys" "$dest/config/keys.json"
```

`cmp` 失败就停。不要删除原来的 keys 文件。备份目录是 `$HOME/search-boost-backups/store-<UTC时间>`，目录 `0700`，其中的文件 `0600`。

POSIX 上，本程序创建的配置目录是 `0700`，keys 文件是 `0600`。写入先做 `0600` 临时文件再改名，不会把已有文件改得更宽。Windows 没有这些权限位，由 ACL 继承。

### 3. 安装或升级到本候选

软件包和配置不是同一个目录。安装替换的是 npm 全局命令，不写 keys。

```bash
npm install -g /absolute/path/to/search-boost-0.3.1-beta.4.tgz
search-boost --version
cmp -- "$keys" "$dest/config/keys.json"
```

`--version` 必须打印 `0.3.1-beta.4`。`cmp` 仍必须成功。然后：

```bash
search-boost refresh -y
```

`refresh` 只用当前包刷新已经存在的宿主接入，不删除 keys，也不安装还没有的宿主。它改宿主配置时，会在 SearchBoost 根目录下的 `backups/upgrade-<时间>-<uuid>/` 留下那次托管文件的副本：目录 `0700`，文件 `0600`，里面有 `manifest.json`。那是宿主文件的回滚副本，不能代替上面的整库备份。

两个进程同时写 keys 时，后一个得到冲突错误，先写入的文件保持原样。崩溃留下的锁超过 30 秒视为放弃。写到一半失败时，临时文件会被删掉，原来的 keys 还在。不要在 TUI 或 refresh 还没退出时做还原。`refresh` 报部分失败时，先读它给出的备份路径，等这个进程退出后再重试。不要同时开第二次 refresh。

### 4. 回滚软件包

回到上一份 beta tarball 时，用那份文件再执行一次全局安装，然后 `search-boost --version`。配置备份不会被这次安装删除。回到 GitHub `v0.3.0` 提交 `12428996dd1aef92f0aedf78ed77066fd59cdbec` 时，用这份提交打出的包，不用 registry。没有这份 git 仓库时，向持有该提交的人要打好的 tarball，仍然不要执行 registry 安装。有仓库时：

```bash
git archive --format=tar -o /tmp/search-boost-v0.3.0.tar 12428996dd1aef92f0aedf78ed77066fd59cdbec
mkdir -p /tmp/search-boost-v0.3.0
tar -x -C /tmp/search-boost-v0.3.0 -f /tmp/search-boost-v0.3.0.tar
(cd /tmp/search-boost-v0.3.0 && npm pack --ignore-scripts)
npm install -g /tmp/search-boost-v0.3.0/search-boost-0.3.0.tgz
search-boost --version
```

`npm pack --ignore-scripts` 只避免 tag 上的 `prepublishOnly` 在打包时跑完整测试。后面的 `npm install -g` 不加 `--ignore-scripts`。`--version` 必须打印 `0.3.0`。`npm pack` 的字节会随时间变化，身份以提交 `12428996dd1aef92f0aedf78ed77066fd59cdbec` 为准。

### 5. 回到 0.3.0 之后核对 DeepSeek Base URL

0.3.0 的代码是 Anthropic messages：默认基址 `https://api.deepseek.com/anthropic/v1`，请求 `{base}/messages`，工具 `web_search_20250305`。keys 文件不会被安装改写。

先确认 PATH 上的 `search-boost` 已经是 0.3.0，再执行：

```bash
search-boost config keys --show
```

如果 DeepSeek 的 Base URL 是 `https://api.deepseek.com` 并且标成自定义，0.3.0 会请求 `https://api.deepseek.com/messages`，那不是 0.3.0 的默认。用这个 0.3.0 二进制清掉保存的基址：

```bash
search-boost config keys --reset-base-url deepseek-search
search-boost config keys --show
```

DeepSeek 那一行必须变成 `https://api.deepseek.com/anthropic/v1`，并标成默认。其他引擎的自定义基址保持原样。

不要在 beta.4 仍是当前命令时把 DeepSeek 基址设成 `https://api.deepseek.com/anthropic/v1`。beta.4 会把这条旧路径当成遗留端点，请求不会发出。在 beta.4 上执行 `--reset-base-url deepseek-search` 只会清掉保存的覆盖，显示的默认值是 beta.4 自己的 `https://api.deepseek.com`。这样可以避免 0.3.0 继承一条写成 `https://api.deepseek.com` 的自定义基址，但 anthropic 默认值要等 0.3.0 的 `--show` 来确认。

### 6. 还原 keys

只在第 2 步的 `cmp` 已经成功，并且没有 TUI 或 refresh 还在写配置时还原。还原单独的 keys 文件，避免把整棵状态目录盖回旧副本：

```bash
cp -a -- "$dest/config/keys.json" "$keys.new"
cmp -- "$dest/config/keys.json" "$keys.new" || { rm -f -- "$keys.new"; echo 'restore stopped; live keys unchanged'; exit 1; }
chmod 600 "$keys.new"
mv -- "$keys.new" "$keys"
```

`cmp` 失败时删掉 `$keys.new`，原来的 `$keys` 不动。`mv` 在同一块文件系统上是改名。还原不会删除 `$HOME/search-boost-backups`。要回到本候选时，再安装 beta.4 的 tarball；安装不会自动把备份拷回去。

### 7. 本机如何核对过这些步骤

核对脚本是 git 里的 `scripts/verify-v031-beta4-config-backup.mjs`。它不在 npm 包里，也不会进入 `npm run test:isolation`。它先把 `HOME` 和 npm prefix 换到临时目录，再执行上面的 `config keys --show`、备份、`cmp`、失败则不替换、beta.4 与由该 git 提交打出的 0.3.0 包上的 Base URL 显示。脚本打印的临时目录不是用户应使用的路径。并发写锁的 30 秒冲突没有在这个脚本里再跑一遍，仍是现有写入实现：后写者报冲突，失败的写入留下原文件。

没有付费 live 调用。脚本没跑到的步骤标 NOT RUN。
