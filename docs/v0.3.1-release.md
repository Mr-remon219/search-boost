beta.5 的包保留，不改名，也不当作 0.3.1：`/opt/cursor/artifacts/search-boost-0.3.1-beta.5-70e25a5.tgz`，sha256 `43af18b318be7263a5da80aa2f719e024be7aef4d2a52bab66a61d157f1f8a2f`。

这一步不打 tag，不发 GitHub Release，也不 `npm publish`。核对时 registry 的 `latest` 是 `0.2.4`，`beta` 是 `0.3.0-beta3`，版本列表里没有 `0.3.1`。GitHub 没有 `v0.3.1` tag 或 release。不要执行 `npm install -g search-boost@0.3.1`、`npm install -g search-boost@latest` 或 `npm install -g search-boost@beta`。

安装这份候选：

```bash
npm install -g /absolute/path/to/search-boost-0.3.1.tgz
search-boost --version   # 必须打印 0.3.1
```

安装替换的是 npm 全局命令，不写 keys。然后 `search-boost refresh -y` 只刷新已经存在的宿主接入，不删除 keys。

## 行为从哪来

行为就是 beta.5 那棵树。beta.1 到 beta.5 的字段、路由、升级和 TUI 说明仍在包内，不在这里重写。`deepseek-search` 只调用官方 `POST /v1/tools/search`。配置基址在 `engines.<name>.baseUrl`，不是顶层 `baseUrls`。

beta.5 之后已经有真实 XFCE 工程复核，以及独立的纯用户有界 mock GO。那次通过针对的是 beta.5 的行为。本候选不改产品逻辑，因此不把更早的云端记录说成否定了那次桌面实操，也不把本包说成又做了一次桌面终审。

## 回滚和备份

可执行步骤仍是 [0.3.1-beta.4 说明](./v0.3.1-beta4-release.md) 里的定位、备份、`cmp`、还原和 Base URL 核对。这里只改身份：

- 配置位置以 `search-boost config keys --show` 打印的 `File:` 或 `文件：` 为准。
- 备份放在配置根目录外面，目录 `0700`，文件 `0600`。`cmp` 失败不要覆盖原文件。还原先写到旁边的新文件，比对成功再 `chmod 600` 并 `mv`。
- 两个进程同时写 keys 时，后一个报冲突，原文件留下。崩溃留下的锁超过 30 秒视为放弃。写到一半失败会删掉临时文件。
- 不要在 TUI 或 `refresh` 还没退出时还原。`refresh` 改宿主配置时，会在 SearchBoost 根目录的 `backups/upgrade-<时间>-<uuid>/` 留下那次托管文件的副本。那不是整库备份。安装失败时保留上一份 tarball，再装回去；不要假定全局目录一定完整。
- 回到 GitHub `v0.3.0` 时，用 annotated tag `12428996dd1aef92f0aedf78ed77066fd59cdbec` 剥出的提交 `61c428b786230e71d7a84b2c417da4a9ac246d54` 打出的包。registry 上没有 `0.3.0`。
- 若文件里 DeepSeek 的 `engines.deepseek-search.baseUrl` 是 `https://api.deepseek.com`，0.3.0 会请求 `https://api.deepseek.com/messages`。换成 0.3.0 二进制之后，再执行 `search-boost config keys --reset-base-url deepseek-search`。`--show` 应显示默认 `https://api.deepseek.com/anthropic/v1`。其他引擎的自定义基址保留。不要在 0.3.1 仍是当前命令时把 DeepSeek 基址写成 `https://api.deepseek.com/anthropic/v1`，这条旧路径不会发出请求。
