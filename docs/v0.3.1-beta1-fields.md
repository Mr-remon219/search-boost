# 0.3.1-beta.1 来源字段契约

MCP、CLI 摘要、Pi 和 DSH 的 `fused_search` 使用同一结果对象。没有并列的第二套状态字段。

| 字段 | 含义 |
| --- | --- |
| `routeExplanation` | 为什么是这些引擎。不表示又调用了别的引擎。 |
| `engines` / `enginesUsed` | 结果来自哪些引擎，以及这次实际用过的引擎。 |
| `engineStats.<name>.attempts` / `successes` / `errors` | 计划调度次数、成功次数、失败次数。一次调度里的 HTTP 重试不加进 `attempts`。 |
| `engineStats.<name>.transportRequests` | 可选。该调度里的 HTTP 次数，含重试。没有内部重试的引擎不带这个字段。它不等于 `attempts`。 |
| `engineStats.<name>.note` | 失败类：`http_401`、`timeout`、`missing_key`、`invalid_request`、`cancelled` 等。不含响应正文和 Key。整条 note 最长 120 个 JavaScript 字符。超出时保留开头和结尾，中间用 `…`，不再只留开头。 |
| `outcome` | `results` 有命中；`partial` 有命中且至少一家失败；`empty_success` 是被调用的引擎 HTTP 成功但零条；`unavailable` 一家都没调用；`failed` 调用过且全部失败。它不增加请求。 |
| `results[].title` | 引擎没给标题时是空字符串。不用 URL 填标题。 |
| `results[].url` | 引用地址保留路径、查询和非空片段，所以章节 `#` 仍可引用。单独的末尾 `#` 去掉。用户名或密码、非 http(s) 的地址整行丢弃，不当成命中。 |
| `results[].provenance` | 去重后每一家仍留一条，并保留那一家自己的 URL，包括片段。`summary` 按该来源原样记录：缺失就没有这个键，`null` 保持 `null`，`""` 保持 `""`，非空保持原文。不把另一家的 null 或空串抄到缺失的来源上。 |
| 去重键 | 协议和主机小写，去掉 `www`、路径末尾斜杠、片段和跟踪参数（`utm_*`、`pk_*`、`mtm_*`、`via`、`fpr`、`gclid`、`fbclid`、`mc_cid`、`mc_eid`）。`#a` 与 `#b` 是同一篇文档，合成一行，但引用 URL 和各源 provenance 仍带各自片段。路径大小写和其他查询参数保留，所以 `?id=1` 与 `?id=2` 不合并。 |
| `url` / `title` / `snippet` | 证据。`snippet` 是短摘录，给 UI。空字符串保持空，不用 URL 或 summary 填。 |
| `summary` | 可选。官方 Search 的长摘要，给 agent。主行的选择见下一节。不写入 `snippet`。 |
| 元数据不足 | 合并后的一行如果 title、snippet、summary 去空白后都为空，不计入命中。`warnings` 写明 `Omitted a hit with no title, snippet, or summary`，并带上引擎和原始 URL（含片段）。不补标题或摘要。被调用的引擎仍算成功时，`outcome` 是 `empty_success`，不是新的第六态。 |
| `siteName` / `authority` / `rerankScore` / `published` | 来源有则保留。未知为 null，不编造。 |
| `provenance` | 去重前的观察。合并后的行仍能看到引擎、名次和 URL。 |
| 工具是否错误 | 结果为 0，且没有任何一次成功调度（选定源都没被调用，或每次调用都失败）。HTTP 200 且 `results` 为空是成功零条，不是错误。部分引擎失败但仍有结果不是错误。 |

## 同一 URL 的 summary 选择

主行是排序赢家，与输入顺序无关：查询词重合多的优先，其次是更好的名次，再是稳定 JSON 键。

- 主行已有非空 `summary`：保持主行原文。另一家不同的非空摘要只留在那一家的 provenance。
- 主行缺失、`null` 或 `""`，且另一家有非空摘要：顶层改成那段非空摘要。各源 provenance 仍是原来的缺失、`null`、`""` 或非空。
- 主行缺失，另一家只有 `null` 或 `""`：顶层继续没有 `summary` 键。不把 missing 写成 `null`。
- 主行是 `null`，另一家缺失或 `""`：顶层保持 `null`。
- 主行是 `""`，另一家缺失或 `null`：顶层保持 `""`。
- `snippet` 只在主行 snippet 为空时用另一家的 snippet 补，不抄进 `summary`。

三源同样适用：只有非空文本能补上主行的空摘要；provenance 三条各自保留 missing、`null`、`""` 或非空。

## 五态 outcome

`results`、`partial`、`empty_success`、`unavailable`、`failed` 出现在 CLI 摘要、Pi 文本、DSH 文本、MCP 成功的 `structuredContent`，以及 MCP 把这次搜索标成 `isError` 的 `structuredContent`。schema 含这五个枚举。没有搜索结果对象的意外异常仍然只有错误文本，不伪造 outcome。

HTTP 200 且零条仍是成功：`isError` 为 false，`outcome` 为 `empty_success`。一家都没调用，或调用过且全部失败，仍是工具错误。

去重键仍是现有的 URL / X post id。标题和摘录按上面的主行规则保留，后来的来源记入 `provenance` 和 `engines`。顺序仍由现有共识分和稳定键决定。

文本清理只做：NFC、去掉控制字符和双向控制符、解码六个命名实体、去掉简单 HTML 标签。`a < b` 保留。这不是证据真伪判断。
