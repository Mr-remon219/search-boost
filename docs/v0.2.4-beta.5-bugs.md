# v0.2.4-beta.5 问题记录

按用户报告顺序编号。本文件记录已观察到的问题与验证边界，不代表问题已经修复。

## BUG-001：Update 无法完成旧式 Grok 插件登记的升级

- **状态**：已确认，待修复。
- **发现日期**：2026-10-02（UTC）。
- **影响版本**：SearchBoost `0.2.4-beta.5`。
- **现场版本**：Grok `1.0.5 (5115b46bc9)`，Node `22.23.1` 下的全局 SearchBoost 安装。
- **影响范围**：Grok 插件刷新步骤；不等于 npm 主包升级失败，也不说明其他宿主接入全部失败。

### 用户操作与报错

用户安装新版 npm 包后，通过 Update / `search-boost upgrade --sync-only -y` 刷新已有接入，Grok 步骤报告：

```text
Cannot verify the updated Grok plugin source or legacy registration.
No uninstall/reinstall was attempted and no trust was granted.
```

随后提示完全退出 Grok，并在用户明确授权信任当前源码后，以 `--keep-data` 卸载旧插件、使用 `--trust` 安装当前源目录，再重试同步。

### 只读检查结果

以下结果来自现场 CLI 和文件检查；调查期间未执行插件更新、卸载、重装或信任操作。

| 检查项 | 观察结果 |
| --- | --- |
| npm 主包版本 | `0.2.4-beta.5` |
| `grok plugin list --json` 的插件名 | `grok-plugin-23a3506e`（旧式名称） |
| 登记的源路径 | 当前 npm 包的 `search-boost/grok-plugin` 目录，路径匹配检查为 `true` |
| 缓存位置 | `~/.grok/installed-plugins/grok-plugin-23a3506e` |
| 当前源目录的 `plugin.json` | `name: search-boost`、`version: 0.2.4-beta.5`，`author` 为对象 |
| Grok 缓存的 `plugin.json` | `name: search-boost`、`version: 0.2.0`，`author` 为字符串 |
| 缓存与源目录的文件比较 | `plugin.json`、`README.md` 内容不同；未发现源文件缺失 |
| `grokPluginPayloadMatches` | `false` |
| 更新后登记检查 | `false`：列表中的插件名不是 `search-boost` |

现场源目录为：

```text
/home/mrremon/.local/share/fnm/node-versions/v22.23.1/installation/lib/node_modules/search-boost/grok-plugin
```

该路径仅为现场证据，不是可硬编码的产品路径。

### 已确认的代码问题

相关代码：

- `lib/grok-plugin.mjs`：`findInstalledGrokPlugin` 支持通过源路径或 manifest 识别旧式插件登记。
- `lib/upgrade/integrations.mjs`：`refreshGrokPlugin` 更新前使用上述兼容识别；源路径匹配时调用 `grok plugin update <已登记插件名>`。
- 同一函数更新后的验证却仅接受 `p.name === 'search-boost'` 且源路径匹配的登记，未沿用旧式名称的兼容识别。
- `lib/grok-payload.mjs`：`grokPluginPayloadMatches` 独立检查缓存 manifest 身份、文件集合与字节内容。

**结论**：SearchBoost 更新前后的登记身份验证规则不一致，是已确认的旧登记升级兼容缺陷。用户环境的旧安装状态触发了该路径；现场源路径正确，没有证据表明用户配置错误。

### 尚未查明的部分

Grok 缓存确实仍为 `0.2.0`，因此报错不只是名称检查的误报。现有现场证据尚不能确定原生更新没有刷新缓存的具体原因：可能涉及 Grok 对旧式登记、本地源或旧 manifest 的处理，需要另行复现或查证。

不得将“Grok 原生更新存在缺陷”写成已确认结论；也不得仅放宽插件名检查后就报告更新成功。

### 修复要求与验收方向

1. 更新前后使用一致的插件身份识别规则；旧式名称不能单独构成验证失败，名称或 `repo_key` 也不能单独证明归属。
2. 继续验证当前源路径和缓存 payload；旧缓存、内容不一致或无法验证时仍须报告失败。
3. 区分旧登记身份问题与缓存未刷新问题，给出准确诊断和恢复提示。
4. 保持现有信任边界：未经明确授权，不自动执行卸载/重装，不添加 `--trust`，不改变启用或权限状态。
5. 增加隔离回归，至少覆盖：
   - 旧式列表名称、正确源路径、缓存已更新：验证不得仅因列表名称不同而失败。
   - 旧式列表名称、正确源路径、缓存仍旧：必须失败，不得误报成功。
   - 外来插件、错误源路径或不可验证缓存：不得被当作已更新的 SearchBoost 插件。
   - 已禁用插件及需要重新信任的场景：保留宿主控制，不擅自启用或授予信任。

### 临时处理方式

完全退出 Grok 后，只有在用户明确同意信任当前源码时，才考虑按错误提示卸载旧登记（`--keep-data`）并从当前 npm 包的插件目录重装（`--trust`），然后重试 `search-boost upgrade --sync-only -y`。

此方式尚未在本次调查中执行或验证，不能视为已经修复 BUG-001。

### 子问题 A：失效的历史项目记录持续阻塞整体完成状态

代码证据：

- `lib/upgrade/state.mjs`：`recordedProjects` 读取状态根目录下的 `state/upgrade-projects.json`；`recordUpgradeProject` 累积登记项目路径，未提供失效条目清理流程。
- `lib/upgrade/integrations.mjs`：`discoverIntegrations` 合并当前目录、已登记项目、Antigravity workspace 等来源。目录不存在时追加 `Recorded project unavailable` 警告并跳过，不清理该记录。
- `lib/upgrade/index.mjs`：只要 `plan.warnings` 非空，整体 `ok` 就为 `false`，即使其余可用接入全部成功。

**已确认**：失效记录在重试中重复出现，并持续影响整体完成状态。后续 PowerShell 只读检查确认五条路径均存在于 `C:\Users\Administrator\.search-boost\state\upgrade-projects.json`。这确认了当前登记来源，不证明最早写入者或测试污染时间。

**来源线索，尚非完整归因**：`scripts/test-install.mjs` 的 Grok fresh-install fixture 使用 `sb-grok-fresh-` 临时目录，安装时登记项目，随后删除目录。用户日志的目录名与该 fixture 一致，提示可能是历史测试留下的登记污染。当前测试已有首条 isolation import，且断言登记进入隔离 HOME；不能由现存条目断定 beta.5 的隔离仍在失效，也不能断言用户手工配置错误。

### 子问题 B：Codex 的 SearchBoost 托管标记异常导致刷新失败

代码证据：

- `lib/codex-native.mjs`：`managed` 解析独立 TOML 语句中的 `# SEARCH_BOOST_WEB_SEARCH_START` / `# SEARCH_BOOST_WEB_SEARCH_END`。
- 没有标记时正常返回；开始/结束标记不各为一个，或结束标记位于开始标记之前时，抛出用户日志中的 `Incomplete/duplicate SearchBoost web_search marker`。
- `lib/upgrade/integrations.mjs`：`refreshMcp` 在写配置前调用 `migrateCodexNativeSearch`，因此该错误发生在预检阶段，该目标不继续执行更新写入。

**已确认**：Codex 更新遇到了托管标记校验失败，安全拒绝写入是合理行为，但重复运行不能自行解决异常。

**Windows 后续证据**：默认 `C:\Users\Administrator\.codex\config.toml` 中没有独立 START，只有第 594 行的独立 END，属于真实的不成对标记；未修改该文件。通过 WSL 启动的 PowerShell 进程继承了 `CODEX_HOME=/home/mrremon/.codex`，但 Windows 用户级 / 机器级均未设置此变量，因此不能用调查进程的继承值反推原 TUI 实际来源。尚未确认异常最早由谁产生，也未证明原报错一定读取默认文件。配置位置仍必须遵循实际进程 CODEX_HOME，未设置时才使用默认位置。

后续只需先取得标记附近的脱敏内容与位置，不应要求用户提交整个可能含敏感信息的配置。修复时不得粗暴删除所有标记或覆盖整个 TOML，也不得改变用户的原生搜索偏好。

### 子问题 C：DSH 全量串行刷新、无已同步快速路径、重复验证

代码证据：

- `discoverIntegrations` 扫描所有登记 SearchBoost 或旧包的 DSH profile，不区分名称看起来像正式配置还是测试配置；本次共八个目标。不能仅凭 `test-*` / `sb-fix-*` 名称自动删除或跳过用户 profile。
- `lib/upgrade/integrations.mjs`：`integrationResources` 为所有非 MCP 目标分配共同的 `runtime-receipts` 资源。因此 Pi 与各 DSH 目标经 `groupUpgradeJobs` 进入同一串行任务组；`pool(..., 3)` 不等于 DSH profile 三路并行。
- 同文件 `refreshDsh`：即使目标已处于当前版本、没有旧包待迁移，也没有先验证后跳过包管理操作的快速路径；非 dry-run 总会执行宿主 `plugin add`。
- `refreshDsh` 在 `add` 后调用一次 `verifyDshRegistration`，在旧包清理阶段结束后再调用一次；即使 `retired` 为空，也执行第二次完整验证。
- 每次 `verifyDshRegistration` 包含源登记、包版本、payload 与实际宿主 resolver 检查；`verifyDshRuntime` 会额外启动选定宿主的探针进程。

**可由代码确定的工作量**：在八个目标均成功且非 dry-run 的情况下，每次完整刷新执行八次 `add` 和十六次完整登记/运行时验证；首次存在旧包时，还会额外执行 `remove`。第二次重试也不会跳过已同步的 DSH 目标。

**验证边界**：串行调度有共享登记状态的安全原因，不能直接撤掉锁或扩大并发。没有 Windows 阶段计时，尚不能判定主要瓶颈是 pnpm、npm-exec 启动/解析、磁盘/杀毒扫描、备份、payload 检查还是宿主探针。`refreshDsh` 使用配置文件备份；不要把独立安装路径 `runDshInstallTransaction` 的整份 `node_modules` 备份误当作本次 Update 的已证实耗时原因。

### 修复要求与验收方向

1. **失效记录**：区分失效的历史登记、明确指定且不可用的 workspace、真实失败目标。为陈旧条目提供可审查的清理/忽略方式，并避免无关历史目录无限阻塞可用接入的更新完成状态；不擅自删除目录或用户 profile。
2. **测试污染**：追查旧 fixture 登记如何进入真实状态，保留当前隔离断言；以隔离 HOME 中的历史污染样本验证处理流程，不触碰真实用户状态。
3. **Codex 修复**：取得脱敏配置后复现；若为解析错误则修复解析器，若为历史异常块则提供备份、明确诊断及保留原偏好的修复方式。覆盖缺失、重复、逆序标记及多行字符串中的伪标记。
4. **DSH 快速路径**：对已同步且无旧包的目标，完整验证当前登记、版本、实际加载源和 payload 后，避免不必要的 `add`、配置重写与备份。相同版本但内容变化、错误加载源、旧登记或真实需要迁移的目标不能被跳过。
5. **减少重复验证**：明确两次验证各自保护的状态变化；只有在没有相关变更且证据仍有效时复用结果，不以版本号或子进程返回 0 代替实际 payload/resolver 验证。
6. **并发边界**：若优化并发，先缩小或改进共享登记状态的临界区，保持同一 profile、目录别名、共享 manifest/node_modules、Desktop lock 和状态文件的写入隔离。
7. **性能证据**：增加不泄露凭据的目标/阶段计时，在 Windows 对首次迁移与再次同步分别测量宿主派发次数、验证次数、总时长和 profile 内容变化，再判断优化效果。

### 当前处理与限制

最初仅根据用户日志和代码记录；后续获授权实现产品修复并通过 PowerShell 做只读现场检查。没有清理 Windows 项目登记、修复真实 Codex TOML 或删除/更新真实 DSH profile。Windows 安装为 beta.5，命令来自 `C:\Users\Administrator\AppData\Local\pi-node\current`；现场 owning DSH host 与性能耗时未据此推断。

beta.5 检查 `latest=0.2.3` 后拒绝降级属于当前设计，不是本条失败原因；beta 频道发现能力应作为独立需求处理。

## BUG-003：DSH 的 X 搜索与社区融合结果不符合输出 schema

- **状态**：两处输出契约缺陷已离线复现，待修复；同批报告的 `fetch_page` 失败原因仍待确认。
- **影响版本**：SearchBoost `0.2.4-beta.5`。
- **影响范围**：DSH 接入的 `x_search` 与启用 `community` 的 `fused_search`；不据此断言所有宿主都出现相同报错。
- **关联说明**：本条记录用户第三批报告的三个工具错误，区分已确认的 SearchBoost bug 与尚未归因的抓取失败。

### 子问题 A：`x_search` 返回未声明的顶层诊断字段

用户调用：

```json
{"max_results":10,"query":"from:elonmusk","type":"keyword"}
```

重复三次报错：

```text
invalid output: data must NOT have additional properties
```

代码证据：

- `lib/runtime.mjs`：`runXSearch` 在成功与失败返回值中加入 `engineStats`、`enginesUsed`、`warnings`。
- `adapters/dsh/index.js`：`registerXSearchTool` 的输出 schema 未声明上述字段，同时设置 `additionalProperties: false`。
- `adapters/dsh/schema.js`：`registerDshTool` 在交付返回值前使用 Ajv 校验，拒绝未声明字段并抛出 `invalid output`。

**已确认**：使用实际 `runXSearch`、注入的离线 fallback 和 DSH 注册的输出 schema，复现三个顶层字段的 `additionalProperties` 错误。仅移除这三个未声明字段后校验通过。

这是 SearchBoost 核心返回值与 DSH 适配契约不一致，不是用户参数错误，也不能由此判断底层搜索是否找到帖子。重复调用不会解决确定性的契约问题。

### 子问题 B：`fetch_page` 拒绝原站正文，备用 Jina Reader 返回 403

用户抓取 `https://x.com/elonmusk`，报错：

```text
response is not text (text/html; charset=UTF-8); refusing to deliver it as page content; reader failed: jina http 403
```

代码证据：

- `lib/search/fetch.js`：原站正文触发 `looksBinaryType` 或 `looksBinary` 时拒绝交付，再尝试 Reader；Reader 失败信息追加到原始错误。
- `lib/search/pdf.js`：`looksBinaryType` 不将 `text/html; charset=UTF-8` 判作二进制；`looksBinary` 在发现 NUL 字节或特定控制字节占比超过 10% 时判为二进制。
- 离线对照确认：正常 HTML 不触发上述二进制检测，含 NUL 的 HTML 会触发。

**已确认的现象**：按当前实现，此日志对应原站正文的字节检测未通过，且备用 Reader 请求收到 HTTP 403。括号内的 HTML MIME 类型只是服务器声明，并非拒绝 HTML 格式本身。

**尚未确认**：未取得原请求响应正文、相关响应头和传输路径，不能判断字节检测是否误判、是否存在解压/传输异常，也不能确定 403 的具体原因。不得直接写成“X 反爬导致”或“SearchBoost 将所有 HTML 当作二进制”。本子问题保留为待调查现象，不列为已确认的实现缺陷。

### 子问题 C：`fused_search community:true` 泄漏内部字段

用户调用：

```json
{"community":true,"complexity":"medium","max_results":10,"query":"Elon Musk X post latest hours","recency":"day"}
```

重复四次报错：

```text
invalid output: data/results/7 must NOT have additional properties
```

`results/7` 是零起始索引，指第八条返回结果，不是第八个搜索引擎失败。

代码证据：

- `lib/search/x/community.js`：`mergeCommunityResults` 经 `normalizeSearchHit` 保留 `created_at`，再调用 `rankFusedRows`。
- `lib/search/scoring.js`：评分返回内部字段 `bestIndividual`、`groupEvidence`、`votingEngines`；`rankFusedRows` 将它们展开到结果行。
- `lib/search/fusion.js`：普通网页融合路径对结果进行公开字段投影；社区融合路径未执行同样的投影。
- `lib/runtime.mjs`：`runFused` 将社区融合行交付给选择流程并返回。
- `adapters/dsh/index.js`：融合结果行 schema 未声明上述四个字段，同时禁止额外属性。

**已确认**：使用实际 `runFused`、离线引擎和注入的 X 帖子，复现结果行中四个字段的校验错误：

```text
created_at
bestIndividual
groupEvidence
votingEngines
```

首次实验仅移除 `created_at` 后仍失败，暴露其余三个内部评分字段；移除全部四个未声明字段后校验通过。同一离线对照中 `community:false` 的输出通过校验。

这是 SearchBoost 社区结果的公开输出契约问题。原现场未保存完整返回值，因此离线复现确认的是同类缺陷，不能断言现场第八条结果一定含有全部四个字段。

### 修复要求与验收方向

1. 对齐核心返回值与 DSH 输出 schema，保留有用诊断信息；不得仅将所有对象改为允许任意字段来掩盖契约不一致。
2. 明确社区与网页结果共用的公开字段投影，内部评分字段不得无意泄漏；保留公开评分、来源与日期信息。
3. 增加实际核心返回值跨 DSH 校验的隔离回归：覆盖 X 成功、空结果、失败、缓存及并发复用，以及融合搜索社区开启/关闭和 Web/X 混合结果。
4. 调查抓取问题时先取得必要且脱敏的响应头、字节特征与传输信息；保持二进制拒绝、大小限制和网络安全边界，不为抓取 X 关闭保护或绕过 403。

### 验证与当前处理

- 离线复现使用隔离 HOME、实际核心函数与 DSH 注册的输出 schema，无真实搜索或抓页请求。
- `node scripts/test-dsh-schema.mjs` 通过，但现有样例未覆盖上述实际 X/社区返回值，不能作为这两处缺陷不存在的证据。
- 临时关闭 `community` 可避开已复现的社区融合路径，但会失去额外 X 检索；不构成修复，也不保证其他网络请求成功。
- 本次仅诊断并记录，未修改实现、宿主配置、凭据或网络策略，未发布新版本。

## BUG-004：TUI 仅提供文件夹式导航，缺少默认平铺布局

- **状态**：用户体验问题已记录，设计经用户确认，待实现。
- **影响版本**：SearchBoost `0.2.4-beta.5`。
- **问题**：当前首页必须先选择功能分类，再进入具体操作。部分用户希望直接看到全部功能，不需要额外分类层级。
- **确认的方向**：默认采用平铺主菜单；在「TUI 设置 → 菜单布局」中可切换平铺 / 文件夹，并保存偏好。未保存布局的旧配置也默认平铺；保留现有语言及其他配置。
- **排序**：首次配置 → 安装 / 刷新接入 → 更新 → 状态 → 搜索引擎配置 → 默认搜索层 → 工具开关 → X 凭据 → Jev → 原生搜索替换 → MCP 配置片段 → 卸载 → TUI 设置 → 退出。
- **二级设计**：保留必要的对象选择、参数和安全确认，不将分类层重新塞回平铺模式；搜索引擎配置支持任选引擎，更新执行前展示范围并确认。
- **完整设计笔记**：[TUI 平铺 / 文件夹布局设计](./tui-flat-layout-note.md)，含主菜单示意、各入口二级内容、文件夹模式、持久化与验收要求。
- **当前边界**：仅记录设计，未修改 TUI 实现、用户设置或发布版本；两种布局须共享功能与执行逻辑，不扩大权限或改变信任边界。

## BUG-005：Adaptive 候选容量参数未贯穿执行链路，交付范围与容量不协调

- **状态**：参数使用缺陷已离线复现，容量适配问题已确认，待修复；分页配比的现场归因待核实。
- **影响版本**：SearchBoost `0.2.4-beta.5`，schema v5、N_off 单流程。
- **审计范围**：按用户定义，保持现有大框架与逻辑决策，只检查数值设置、参数配比与字段用法；不采纳自动读全文、增加检索轮次、跨问题记忆或硬偏好过滤等建议。
- **明确缺陷**：screening 的有效 `candidateLimit` 作为容量传给共享 fused，但 `lib/runtime.mjs` 的 `selectSnapshot` 仍使用独立硬编码 32。离线请求容量 64、融合池已有 64 条时，实际快照仍为 32；参数没有控制最终截取。
- **容量适配**：输入允许 `max_results=50`，默认审查容量却为 32，33–50 的交付目标即使全部候选合格也不可达。当前已有诚实警告，但按本次审计口径仍需协调数值；具体取值未决定。
- **分页待核实项**：8,000 字符摘录与 45,000 字节软页容量会产生语言相关的碎页。离线十条长 ASCII 结果分为 5+5，十条等字符长度中文结果分为十个单条页；无遗漏、重复或重排。原现场碎页尚未取得完整响应，不能认定为丢页 bug 或直接扩大容量。
- **重要纠偏**：`qualityAssessed` 不是全部评审量。离线 32 个候选全部收到 value 判断，其中 10 个准入、22 个低价值过滤；不能将该字段解读为只审查 10 个。调高 `max_results` 也不会扩大当前快照。
- **完整审计笔记**：[Adaptive 数值与参数用法审计](./adaptive-logic-audit-note.md)，含实验证据、分类、修复边界与验证限制。
- **验收方向**：声明容量与实际执行一致，覆盖缓存、Web/X 共同上限、稳定排序及诊断计数；协调目标范围和筛选余量，不改普通 fused 行为或现有准入语义。分页优化须保留完整摘录、保存集合与零网络读取。
- **当前边界**：六个相关隔离测试入口通过；仅记录审计，未修改实现或评分系数，未确定新的容量数值，也未发布版本。
